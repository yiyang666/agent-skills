# 陌生项目调查手册

本文件规定深读代码前后的调查策略。目标不是“读完每一行”，而是用可复查证据尽快建立项目边界、执行结构和关键数据链路。

## 1. 先固定边界

记录：

- 仓库根目录、HEAD commit、当前分支、工作区 clean/dirty。
- 用户要求的范围和输出语言。
- 既有未提交文件，尤其是与 `project_guide/` 无关的内容。
- 适用的 Agent 指令文件。

创建分支后才允许写指南。整个调查不运行项目代码。

## 2. 首轮文件盘点

优先使用高效文件枚举与搜索工具，建立以下分类：

| 类别 | 常见线索 |
| --- | --- |
| 语言/框架 | 扩展名、框架配置、入口 |
| 构建/依赖 | `package.json`、`pyproject.toml`、`Cargo.toml`、`CMakeLists.txt`、`package.xml` |
| 启动/部署 | launch、Compose、systemd、容器、CI/CD、IaC |
| 接口 | route、controller、RPC、GraphQL、消息/IDL、CLI |
| 状态/数据 | schema、migration、model、store、cache、文件格式 |
| 配置 | YAML/TOML/JSON、环境变量、feature flag |
| 验证 | 单元/集成/E2E 测试、fixture、mock |
| 文档 | README、ADR、设计说明、运维手册 |
| 重资源 | vendor、build、dist、模型、数据集、媒体、生成代码 |

首轮只记录重资源的角色，不读取其完整内容。不要把依赖目录、构建产物或大型模型塞进上下文。

## 3. 识别运行时枢纽

按项目形态定位：

- **Web/API**：服务器入口、路由注册、中间件、Controller/Handler、Service、持久化适配器。
- **事件/队列**：生产者、Topic/Queue 声明、消费者注册、重试与死信。
- **机器人/实时系统**：节点入口、Topic/Service/Action、消息定义、timer/control loop、设备边界、状态机。
- **CLI/批处理**：命令注册、参数解析、任务编排、输入输出文件和退出码。
- **ML/推理**：预处理、模型加载、输入输出 shape、后处理、fallback、硬件后端。
- **前端**：应用入口、路由、状态管理、API client、组件边界、构建配置。
- **库**：导出 API、核心类型、不变量、扩展点和调用示例。

先读入口与注册关系，再读核心实现。通过接口定义判断数据形状，通过配置判断运行时分支。

## 4. 建立组件图

对每个主要组件记录：

- 职责和不负责的内容。
- 上游输入与下游输出。
- 依赖的内部模块和外部系统。
- 生命周期、并发/线程/进程边界。
- 关键配置与默认值。
- 失败、重试、fallback 和反馈路径。
- 最可信的源码位置。

只画能被代码支持的边。仓库外组件要标记为外部或待确认。

## 5. 选择关键数据链路

优先级：

1. 解释项目核心价值的主链路。
2. 贯穿多个组件/包/进程的链路。
3. 带状态转换、副作用或安全边界的链路。
4. 最常被新成员排查或修改的链路。

每条链路都回答：

1. 谁触发，输入类型/字段/单位是什么？
2. 在哪里解析和校验？
3. 如何变换，状态保存在哪里？
4. 哪些配置或 feature flag 改变路径？
5. 核心决策在哪个函数/类？
6. 输出/副作用是什么，谁消费？
7. 错误、超时、取消、重试或反馈如何处理？
8. 哪一段只能推断，缺什么证据？

跨消息、RPC、事件或文件边界时，同时查生产者和消费者。

## 6. 核验已有文档

把 README/设计文档当作“作者意图与搜索关键词”，逐项回到当前代码验证：

- 路径、组件和入口是否仍存在。
- 文档中的默认配置是否与代码一致。
- 构建/运行命令是否符合当前目录布局与 Manifest。
- 文档描述的链路是否在 launch/注册/依赖中真正连通。
- 推荐实现是否有测试、历史或部署证据支持。

发现冲突时记录“文档说什么、代码显示什么、实际环境还需确认什么”。不要悄悄替文档圆场。

## 7. 用版本历史解决疑点

只有当前代码不能解释意图时才查看历史：

- 文件首次引入和最后修改提交。
- 高风险/关键实现是否有后续修复。
- 重命名或架构迁移是否留下旧文档。

提交信息是辅助证据，不等于运行验证。

## 8. 控制分析规模

- 先做广度地图，再对 2–5 条核心链路深读。
- 搜符号、注册关系和配置键，不逐文件线性阅读。
- 二进制/模型只记录存在、引用和大小；未检查内容时明确说明。
- 生成文档前整理“已证实、推断、未知”三类结论。
- 小仓库可以覆盖更多实现；大型 Monorepo 应明确采样范围和未覆盖区域。

## 9. 停止条件

达到以下条件即可开始写指南：

- 能用一段话说明项目目标和边界。
- 能解释主要组件、依赖方向和启动入口。
- 必需的项目结构与数据链路已有源码证据。
- 关键配置、接口、测试现状和外部依赖已定位。
- 最重要的风险/未知项已区分事实与推断。
- 每个重要结论都能给出源码或配置链接。

缺关键证据时不要靠扩大措辞掩盖；把缺口列入待确认项。
