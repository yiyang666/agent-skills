# 陌生项目领航

在不修改项目实现的前提下，为陌生仓库建立可信地图。用同一组代码证据同时生成适合人类循序阅读的学习路线，以及适合 Agent 快速检索、明确时效边界的压缩快照。

## 输入与默认值

开始分析前，从用户请求和仓库中确定：

- **仓库根目录**：用户未指定时使用当前 Git 根目录。
- **输出目录**：固定为 `<repository-root>/project_guide/`。
- **输出语言**：跟随用户语言；文件名、固定元数据字段、代码标识符与源码符号保持原样。
- **分析范围**：用户未限定子系统时覆盖整个仓库。
- **快照模式**：只生成一次性快照，不承诺增量维护。

若 `project_guide/` 已存在，先检查但不要合并或覆盖。询问用户是用新快照替换，还是停止。

## 安全边界

调查过程保持只读。允许读取文件、搜索和检查 Git 元数据或历史。除非用户另行明确授权，不安装依赖、不构建项目、不执行测试、不启动服务、不访问项目端点、不运行迁移、不连接硬件，也不调用仓库脚本。

创建输出文件之前：

1. 读取适用的 `AGENTS.md`、Cursor rules 或同类项目规则。
2. 检查当前分支与工作区状态，保留所有既有变更，绝不暂存它们。
3. 按用户或仓库命名规范新建分支；没有规范时使用宿主环境允许的、含义清晰的 project-guide 分支名。
4. 用户未明确要求提交时，不提交生成的指南。

如果目标目录不是 Git 仓库，或无法创建分支，在写文件前停止并询问用户如何隔离产物。

## 证据规则

按以下优先级判断项目当前行为：

1. 当前源码、接口/Schema、构建清单、启动文件和运行配置。
2. 测试、示例、Fixture、部署定义，以及能反映可执行行为的生成元数据。
3. 当前代码注释与版本历史，只用于解释其他证据无法说明的意图。
4. 现有 README 和参考文档，只作为检索线索，再回到前述证据核验。
5. 推断，必须明确标注为推断。

不得把未核验的文档陈述写成当前事实。把文档冲突、缺失实现、不可达代码、归属不明和环境依赖行为记录到风险或待确认项中。不要把 Secret、凭证或敏感配置值复制进指南。

## 工作流

### 1. 固定快照边界

记录分析前的当前分支、完整 HEAD commit、工作区状态、仓库根目录、日期和范围。区分既有脏文件与新生成的 `project_guide/`。

在检查项目源码前，完整读取 [调查手册](references/investigation-playbook.md)。

### 2. 先盘点，再深读

列举文件并按语言、Manifest、包、源码根目录、接口、配置、测试、资源、生成文件、二进制、Vendor 和已有文档分类。首轮跳过体积大的生成目录、依赖、缓存、构建产物、模型和二进制内容，但记录它们的用途。

不要顺序通读每一个源码文件。先定位结构枢纽：入口、注册代码、launch/部署定义、中心接口、共享状态、配置加载器、编排循环和公开 API。

### 3. 建立架构地图

确认：

- 项目解决什么问题，边界内外分别是什么。
- 静态证据显示它如何构建、启动、配置和测试。
- 主要组件及各自职责。
- 依赖方向，以及进程、包、线程、服务或硬件边界。
- 对外契约：消息、Schema、Endpoint、命令、事件、文件、数据库表或设备协议。

每个重要架构结论至少链接到一处具体源码。跨边界结论使用多处证据。

### 4. 追踪关键数据链路

沿真实代码端到端追踪最重要的流程：

`触发/输入 -> 解析/校验 -> 转换/状态 -> 核心决策 -> 副作用/输出 -> 反馈/错误路径`

写出准确入口、中间函数或回调、传递的数据形状、会改变行为的配置和可观察输出。遇到发布、入队、RPC 或回调注册时继续追踪生产者与消费者，不要在接口边界提前停止。

小项目至少追踪一条核心链路；较大项目优先选择能解释多数运行行为的 2–5 条链路。无法静态确认的片段必须明确说明。

### 5. 建立开发定位图

找出未来常见任务的高价值入口：新增功能、修改配置、调整接口、排查启动、跟踪运行数据和验证变更。可以从 Manifest 与现有文档推导命令，但用户未授权执行时统一标记为“未执行”。

### 6. 编写指南

写文件前完整读取 [输出契约](references/output-contract.md)。

只有调查已经形成连贯结论后才创建 `project_guide/`。阅读顺序放在 `README.md` 中；按项目特性增加真正有助于学习的章节。始终生成：

- `README.md`
- `project-structure.md`
- `data-flow.md`
- `agent_note.md`

使用相对 Markdown 链接。源码证据优先写成 `[symbol](../path/to/file.ext#L123)` 或行范围链接；必要时同时保留人可读的 `path/to/file.ext:123` 定位。图必须有正文解释，Mermaid 可选，不能成为唯一说明。

### 7. 校验与交付

若有 Python 3，运行：

```sh
python3 <skill-directory>/scripts/validate_guide.py <repository-root>
```

否则手工执行 [输出契约](references/output-contract.md)中的同等检查。修复断链、缺少必需文件、无证据结论、含糊阅读顺序和缺失快照元数据。

交付时报告：新分支、生成文件、快照 commit、分析前工作区是否已脏、校验结果和关键未知项。不要提交。

## Agent Note 生命周期

把 `agent_note.md` 视为昂贵首次调查的压缩产物，不是长期项目真相。

- 只使用一个文件，优先机器扫描效率而非叙事友好。
- 用稳定 YAML frontmatter 标记 commit、分支、原始工作区状态、日期、范围和 `maintenance: one-shot`。
- 明确警告：仓库变更后先核对当前代码；影响实现决策的结论必须重新验证。
- 不创建 `AGENTS.md`、Cursor rules、hook 或其他自动发现机制来加载它。
- 后续代码变更时不增量更新；只有用户明确要求重新生成完整快照时才更新。
