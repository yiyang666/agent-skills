# 工作模块文档生成

根据代码证据生成两份可以直接使用的文档。把“实现设计”作为 README 的主体，把“测试人员如何把模块跑起来并判断结果”作为 TEST_GUIDE 的主体。

## 输入与输出

输入至少包含模块路径；也可包含模块名称、运行环境、启动方式、关联服务、指定提交或变更范围。

默认在模块根目录生成或更新：

- `README.md`：模块定位、边界、架构、时序、接口与关键设计。
- `TEST_GUIDE.md`：环境准备、启停、日志、常用命令、简单测试场景与预期结果。

若模块已有同名文件，先阅读并保留仍然正确的内容，只做有证据的增补与修正。不得无提示覆盖用户手写信息。

## 工作流

### 1. 确定范围

1. 解析模块的绝对路径、仓库根目录与输出位置。
2. 读取仓库规则文件、构建文件、依赖清单、容器配置、启动脚本和已有文档。
3. 若用户指定提交、分支或变更范围，优先分析该范围；否则分析当前模块现状。
4. 路径或模块边界不唯一时，先列出候选并询问，不要扫描无关大型目录。

### 2. 建立证据清单

按以下顺序寻找证据，并记录文件路径或符号名：

1. 入口：主函数、服务注册、路由、ROS/ROS2 节点、launch 文件、任务调度器。
2. 边界：公开接口、消息/Topic/Service/Action、HTTP/RPC、数据库、文件与设备 I/O。
3. 主流程：调用链、状态变化、线程/进程/协程关系、异常与重试路径。
4. 配置：配置文件、环境变量、默认值、端口、模型/资源路径。
5. 运维：启动、停止、健康检查、日志、指标、诊断命令。
6. 验证：现有单元测试、集成测试、示例程序、CI 命令与可复现手工步骤。

必要时使用精确代码搜索和 Git 历史辅助理解，但不要把提交信息当作当前代码行为的唯一证据。

### 3. 处理不确定信息

- 只陈述可以由代码、配置或用户说明支持的事实。
- 无法确认的端口、进程名、命令、返回值或依赖写成 `待确认`，并附上缺少的证据。
- 不运行会写入外部系统、控制真实机器人、修改设备状态或破坏数据的命令。
- 可以运行只读检查、帮助命令和安全的本地测试；执行前遵守仓库规则。
- 不把 Token、Secret、Cookie、私钥、内网凭证或真实个人信息写入文档。

### 4. 生成 README.md

先读取 [README 结构规范](references/readme-structure.md)，再以 [README 模板](assets/README.template.md) 为骨架。根据模块实际复杂度删减无内容章节，不为凑结构编造内容。

必须优先保证：

- 功能、输入输出和模块边界清楚。
- 目录树只展示有设计意义的目录和文件，并解释职责。
- 至少一张与代码一致的 Mermaid 架构图。
- 存在跨组件交互时，提供 Mermaid 时序图；纯库模块可改为调用流程图。
- 说明关键接口、配置、错误处理、并发模型、日志与已知限制。
- 记录关键设计选择及其权衡，而不是逐文件复述代码。

### 5. 生成 TEST_GUIDE.md

先读取 [测试指南结构规范](references/test-guide-structure.md)，再以 [测试指南模板](assets/TEST_GUIDE.template.md) 为骨架。

测试场景保持简单、可执行、可观察，至少覆盖：

1. 正常启动或核心成功路径。
2. 一个边界输入或配置变化。
3. 一个常见异常或依赖不可用场景。
4. 模块存在状态、并发、重连或恢复逻辑时，再增加对应场景。

每个场景都写清前置条件、操作步骤、预期结果、日志/状态观察点和必要的恢复动作。不要虚构“测试通过”；未实际执行时标明“文档场景，待测试部执行”。

### 6. 校验与交付

1. 对照代码复核名称、路径、命令、参数、默认值、端口和图中交互方向。
2. 检查 Markdown 链接、代码块和 Mermaid 语法。
3. 按 [交付检查清单](references/validation-checklist.md) 逐项核对两份文档。
4. 若安全且成本合理，执行文档中的启动帮助、配置校验或现有测试命令；不得为了验证文档启动生产服务。
5. 交付时简述分析范围、生成/更新的文件、实际执行的验证、仍待确认的事项。

## 更新原则

- 代码与文档冲突时，以当前代码和配置为依据，并明确修正文档。
- 只更新受本次代码改动影响的章节，避免无意义的全篇改写。
- Mermaid 节点使用稳定的组件名，不塞入大段实现细节。
- README 与 TEST_GUIDE 对相同命令、进程名和日志路径必须保持一致。
