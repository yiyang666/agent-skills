# README 结构规范

1. 写作目标
2. 推荐章节

5. 完成标准

## 1. 写作目标

README 用于让新接手模块的开发者快速回答：模块解决什么问题、位于系统哪里、与谁交互、核心流程如何运行、为什么这样设计、如何配置与定位故障。

它不是逐文件注释，也不是只写安装命令的项目首页。设计内容应占主体。

## 2. 推荐章节

### 2.1 模块概述

- 一句话定位。
- 所属系统与上游/下游。
- 核心能力列表。
- 明确不负责的范围。

### 2.2 输入、输出与依赖

使用表格描述输入、输出、协议/数据类型、来源/去向和关键约束。列出强依赖与可选依赖，并说明依赖不可用时的行为。

### 2.3 目录结构

只列出承担入口、核心逻辑、接口、配置、测试和脚本职责的路径。每个条目说明职责，不复制完整仓库树。

### 2.4 架构设计

- Mermaid 图展示模块内部组件以及外部依赖。
- 图后解释组件职责、依赖方向和进程/线程边界。
- 涉及前后端、算法模块、消息总线或设备时，明确数据与控制方向。

### 2.5 核心流程与时序

选择最能代表模块价值的一到三个流程：初始化、主成功路径、异常恢复。跨组件交互使用 `sequenceDiagram`；纯算法或纯库调用使用 `flowchart`。

图后说明触发条件、关键状态、超时/重试和完成条件。

### 2.6 接口与数据模型

只写模块边界处的重要接口，不复制所有内部函数。可覆盖：

- HTTP/RPC 方法、请求与响应。
- ROS/ROS2 Topic、Service、Action。
- 消息队列主题与事件。
- 公共类、函数或 SDK 入口。
- 持久化模型、配置模型或文件格式。

每项至少包含方向、用途、主要字段/参数和失败语义。

### 2.7 状态与并发模型

模块存在状态机、多线程、多进程、异步任务、锁或共享资源时必须说明；否则删除此节。指出状态转换、所有权、调度方式和竞态规避策略。

### 2.8 配置与运行

列出配置文件、环境变量、默认值来源、启动命令、健康检查和停止方式。敏感值只写变量名和获取方式，不写真实值。

### 2.9 异常处理与可观测性

描述错误分类、返回/退出行为、重试与降级策略、日志位置、关键日志字段、指标和常见诊断入口。

### 2.10 关键设计决策

用“背景—选择—原因—代价/限制”记录真正影响维护和扩展的决定。没有代码或历史证据时不要臆测设计动机。

### 2.11 已知限制与扩展点

区分当前限制、技术债和计划扩展。不要把没有依据的设想写成路线图。

### 2.12 开发与验证

保留最短可复现的构建、格式检查、单测和集成验证命令，并链接 `TEST_GUIDE.md`。

## 3. 图表要求

- 图必须与正文使用相同组件名。
- Mermaid 节点保持简短；实现细节放在图后。
- 时序图包含失败分支时使用 `alt`/`else`，避免复制两张近似图。
- 不确定的交互不得画成确定事实。

## 4. 内容取舍

- 小型库可合并“输入输出、接口、核心流程”。
- 单进程同步模块可删除“状态与并发模型”。
- 没有部署职责的模块不写伪造的部署章节。
- 目录结构、功能介绍、架构设计和核心流程原则上不可同时缺失。

## 5. 完成标准

- 新开发者能在十分钟内找到入口、配置和关键流程。
- 架构图能解释模块边界，不只是文件列表。
- 命令可复制，路径与代码一致。
- 所有未知信息明确标记，没有伪造测试结论。
